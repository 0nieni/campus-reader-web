# 公告加载优化（2026-10-18）

## 用户可见行为

登录恢复和工作区验证完成后，同时启动学校目录、已选学校的数据库公告查询、学校公开来源刷新。公告列表不再等待目录的后续分页或官网读取。学校目录有独立加载状态，完整加载后才显示“没有找到自己的学校？联系客服添加”，保留原有完整目录要求。

已有公告先显示并允许阅读。来源刷新失败不清空已保存列表；首次没有匹配的已保存公告时显示正在检查来源，采集完成后自动再查询一次。若另一个请求已持有该校刷新锁，仅在当前学校仍有效时最多补查三次，不建立无限轮询。

后台发现变化时提示“公告有更新”，用户点击“显示更新”后更新列表，保留已打开的正文；更新前暂停旧游标的“加载更多”。服务端通过实际新增/变更的行判断变化；命中已有源缓存返回 changed=false，避免把同一缓存检查当作新公告。

## 登录会话内缓存

仅缓存当前账号的列表元数据，不缓存正文，不写 localStorage/sessionStorage 或共享 CDN。按 UID、学校、关键词、时间、全部分类组合分键，五分钟有效，最多八个组合，每个最多一百条。缓存恢复前仍需完成学校选择的服务端授权；退出、账号变化或重新连接时清空。已知超过365天的发布时间使缓存失效，标签变更清除该校旧筛选缓存。

切换回已浏览的学校时先恢复已读列表，再查询服务端首屏。没有变化时保留已加载分页和游标；有变化时提示更新，避免自动把多页列表缩成第一页。服务端返回更短/空结果时应用服务端结果，避免继续展示已删除或过期的尾项。缓存过期或首次访问仍需等待数据库；首次未采集学校仍需等待源站采集。

## 每日有限预采集

复用现有 cleanup 函数和每日18:17 UTC（北京时间02:17）计划，不新增每小时数据库唤醒、函数、后台保活或付费配置。原24小时过期清理先执行；若该阶段超过12秒，则跳过本轮预采集。

学校刷新只记录学校级 lastVisitedAt，以半小时粒度更新，不保存账号或访问流水。每日任务只选择最近七天有人使用且缓存已到期的学校，按最久未预采集优先，每次最多三所。一个北京时间日期只领取一次批次；预采集不更新 lastVisitedAt，避免任务将自己的学校一直保活。只抓公开列表，不预取正文/附件，不调用模型，也不读取 user_profiles、收藏或申请记录。源站仍执行现有域名、DNS、TLS、九秒和大小限制。

新增变化标记、学校活跃时间和任务日期都保存在既有JSON对象中，无新表、迁移或环境变量。公开内容仍与各账号的标签、收藏和私人资料分开授权。

## 验证与限制

前端55项、后端80项回归通过，双方类型检查与Netlify模式生产构建通过。新增测试通过手动控制请求完成顺序，确认官网和目录仍未返回时列表已渲染、空首屏在两种响应顺序下都可补齐、正文不会被后台更新关闭，以及分页恢复、TTL、账号/筛选/个人标签隔离和晚到响应拒绝。真实本地SQL验证每日上限、并发日期锁、活跃筛选、轮换、变化识别及预采集不自续活跃。

这些验证证明加载依赖已拆开，不是线上用户网络的秒数测量。数据库冷启动、用户网络、源站限制仍会影响实际耗时；每日预采集不保证所有学校全天保持最新。线上发布后仍保持未登录拒绝与no-store，不把登录接口或个性化列表改成公开缓存。
