# 阿里云 FC 与邮件提醒配置

实现日期：2026-10-21。先交付代码和预览；阿里云账号、发信域名、真实邮件及真机验收尚未准备，不能把预览当作已经启用外部提醒。原实施依据见 [计划书](aliyun-reminders-plan-2026-10-21.md)。

## 当前实现

网站、受邀账号登录和 SQL 留在 Netlify。阿里云 FC 每分钟签名调用固定生产入口；入口先强一致读取 Netlify Blobs 中的下一唤醒时间，未到期时不创建数据库连接。SQL 保存业务和任务，索引只是唤醒提示。任务改期和取消由版本失效。

浏览器继续使用标准 Web Push。DirectMail 负责邮件，两个通道各自记账和重试。仅邮件账号无需浏览器订阅或 VAPID；关闭邮件也不影响浏览器。所有新账号和历史事项的邮件默认关闭，逐篇明确勾选。两者均不选时保留站内提醒和日历。

前端显示服务待配置、等待首次调度、正常连接、中断或登记失败。每篇事项分别显示未选择、未就绪、已登记、服务已接收、失败、限额或结果未知；服务接收不等于收件箱收到或设备弹出。

## 1. 准备阿里云与发信域名

在本人或团队的实名认证阿里云账号中开通 FC 和 DirectMail。开通、资源包和自动续费是不同操作；本次代码开发没有替你购买或开通任何云资源。

准备可修改 DNS 的自有域名或发信子域名，按 DirectMail 控制台要求验证域名、配置 DNS 并创建发信地址。网站的 `netlify.app` 域名不能代替自有发信域名。

首版锁定 **DirectMail 华东1（杭州）`cn-hangzhou`**，使用官方 `@alicloud/dm20151123` 1.11.0 和对应接口。其它区域使用不同 API 版本，本实现会拒绝不匹配的区域配置，需要先适配和验证，不能只改地址。FC 可以单独选区，但要实测该区到 Netlify 的连接质量。

创建专用 RAM 运行身份，只授权以下 API；服务开通和管理权限留给站点所有者：

```json
{"Version":"1","Statement":[{"Effect":"Allow","Action":["dm:SingleSendMail","dm:SenderStatisticsDetailByParam"],"Resource":"*"}]}
```

发信通过 HTTPS 官方 SDK，固定杭州 API 域名；不公开 SMTP 或浏览器邮件代理。SDK 自动重试关闭，连接和读取均有限时。完整邮箱、服务商响应、令牌和公告不写入日志。

参考：[DirectMail 配置流程](https://help.aliyun.com/zh/direct-mail/getting-started/simplified-procedure-of-sending-by-api-and-smtp)、[各区接口](https://help.aliyun.com/zh/direct-mail/api-dm-2015-11-23-endpoint)、[SingleSendMail](https://help.aliyun.com/zh/direct-mail/api-dm-2015-11-23-singlesendmail)。

## 2. Netlify 环境变量

进入现有项目的环境变量设置。免费套餐 **Scope 保持 All scopes**，它包含 Functions；不需要为单独选择 Functions 升级套餐。Values 选 **Different value for each deploy context**，只填 **Production**，其它环境留空。变量不加 `VITE_` 前缀，不写进 `netlify.toml`、源码或聊天。

- `REMINDER_SCHEDULER`：`aliyun-fc`。
- `REMINDER_TRIGGER_SECRET`：用密码管理器生成至少32字符的随机密钥，与 FC 的同名变量相同。
- `REMINDER_TRIGGER_SECRET_NEXT`：轮换时使用的第二个随机密钥；初次可以不设置。
- `DIRECTMAIL_ACCESS_KEY_ID`、`DIRECTMAIL_ACCESS_KEY_SECRET`：专用 RAM 身份凭据。
- `DIRECTMAIL_REGION`：`cn-hangzhou`。
- `DIRECTMAIL_ACCOUNT_NAME`：已验证的发信地址，必须属于杭州区域。
- `DIRECTMAIL_FROM_ALIAS`：例如 `校园阅览室`，最多15字符。
- `REMINDER_EMAIL_ENABLED`：准备和发布期间先设 `false`；受控验收时设 `true`。
- `REMINDER_EMAIL_DAILY_LIMIT`：建议 `150`；可以调低，实现上限150。

已有 `WEB_PUSH_PUBLIC_KEY`、`WEB_PUSH_PRIVATE_KEY` 继续使用，无需重建。前端只接收公开公钥及服务是否配置，不接收邮件密钥或 HMAC 密钥。

环境变量在部署时固定，修改后需重新部署。即使界面没有付费的 Secrets Controller 选项，仍可按上述方式存储普通服务端环境变量；不要把密钥复制到公开文件。参考：[Netlify Scopes 与环境](https://docs.netlify.com/build/environment-variables/overview/)。

旧 `QSTASH_*` 变量不再被生产提醒链路读取，不必继续填写。确认切换稳定后由持有者移除；这份说明不代表已经检查或删除了线上变量。

## 3. 创建 FC 函数

源码为 `infra/aliyun/reminder-tick.cjs`。打包时将它命名为 ZIP 根目录的 `index.js`；无需 `node_modules` 或任何网站密钥。可直接在 FC 的 Node.js 20 或更高运行时把源码粘入 `index.js`，入口设为 `index.handler`。

仅添加两个变量：

- `REMINDER_TICK_URL`：`https://campus-reader-ninie6159.netlify.app/.netlify/functions/reminder-tick`。
- `REMINDER_TRIGGER_SECRET`：与网站当前验签密钥相同。

FC 不需要数据库连接、DirectMail AccessKey、VAPID 私钥、账号或公告资料。请求只包含空 JSON、时间戳、随机请求编号和签名。网站拒绝其它目标、方法、参数、过期或无效签名；重复调用由任务和通道回执幂等。

先创建函数但保持定时触发器关闭。不开预置实例，最小实例数为0；使用控制台允许的最小资源，最大实例数和并发先限制为1，函数超时30秒。代码网络超时25秒；异步失败重试设为0，由下一次分钟触发及租约恢复，避免额外无限重试。

正式切换后创建一个时间间隔为 **1分钟** 的定时触发器，不为每篇公告创建函数或触发器。参考：[FC 定时触发器](https://help.aliyun.com/zh/functioncompute/time-triggers)。

## 4. 邮箱验证与使用

账号邮箱只来自网站受信任的身份服务；浏览器不能传入任意收件人。后台发送前通过官方 Identity 管理 SDK 再核对当前邮箱，查不到时推迟发送，不使用陈旧快照。验证流程独立于登录邮箱的可选确认字段。

在提醒中心点击“验证当前邮箱”，收到邮件后打开链接，再明确点击确认。验证令牌30分钟有效、单次使用、绑定账号和地址版本；令牌放在 URL fragment，不进入服务器访问日志。GET 不验证或退订，避免邮件扫描器自动触发。验证成功后返回中心点击“检查提醒”，再主动开启邮件。

之后可发送测试邮件，并在每篇事项里勾选邮件。开启账号邮件不会给历史事项补发。新邮箱需要重新验证，旧版本停止后续发送。关闭入口在中心和邮件内都提供；同一地址版本的旧退订链接仍有效。已被服务商接收的邮件无法撤回。

浏览器按设备单独开启，Windows Chrome/Edge、iPhone/iPad 主屏幕网页应用、支持 Web Push 的安卓浏览器都保留设备指引。系统及网络可能延迟显示。

## 5. 限额、反馈与故障

全站每日最多150次邮件发送尝试，每账号20次，验证邮件每账号每天3次、间隔至少60秒；测试邮件也至少间隔60秒。按北京时间日期使用事务计数，包括失败、结果未知和重试，不退款补额度。达到限制会明确显示受限，站内和浏览器继续独立工作。

明确的临时失败有限退避，单个通道最多3次；无效地址或设备停止，网络超时和中断后不能确定服务商是否接收则保留“结果未知”，不自动重发。迟到超过24小时的任务不补发，多个跨过的提前档位合并为最近一次。

只在实际邮件被服务商接收后，安排约30分钟和24小时的 DirectMail 无效地址及垃圾/投诉类反馈查询；每个分钟处理批次最多并行检查四个到期账号。新发送可合并待查时间，空闲且未发信的账号不持续产生维护唤醒。通过供应商鉴权 API 获取结果，只对匹配本发信地址、当前收件地址的硬退信或垃圾反馈暂停邮件，不猜测单封邮件已进入收件箱。该低频维护会计入下一唤醒时间，消耗 API 和 SQL 用量，需纳入测量。查询连续失败时最多尝试三次，之后保留故障计数供人工检查；明确的发信无效地址错误也会立即暂停对应绑定。反馈不是无限期投递保证。

索引缺失或不可用时分钟入口返回503并记录无个人资料的故障事件，不能悄悄改为每分钟扫描全库。每天北京时间09:00、20:00仍有最多100账号、有时间上限的登记修复。用户正常操作也可重建索引。登记未确认的事项不会显示成登记成功。

FC 控制台记录状态码和请求编号；Netlify 日志仅记录处理/接收/失败计数。SQL 通道回执保存预定时间、开始发起时间、结束时间、状态和必要的服务商编号，供后续受控验收。不要把后台数据表或邮箱内容导出到公开 PR。

阿里云设置预算与 FC 错误告警，Netlify 用量达到70%时复核容量；告警不是硬性费用封顶。FC、日志、公网请求、邮件、Netlify 请求/计算/Blobs/SQL 和域名都可能消耗额度或产生费用；本实现不自动升级套餐。价格测算沿用计划书，并在实际开通前核对本人账号权益与地区。

## 6. 发布、切换及停用

先审核 PR，生产配置和账号准备完成后再授权正式发布。七份迁移通过 Git 部署应用，第七份为兼容新增；前六份不改、不直接操作线上数据库。预览隔离生产索引和发送凭据，禁止真实外发。

若旧 QStash 实际启用，先停止旧登记/回调来源并等待至少两分钟，让在途请求结束，再部署新代码；未启用的旧服务无需创建。新代码的旧回调地址固定返回410，不能与 FC 同时消费。未来有效事项迁移为 `aliyun-fc`，已经完成的通知不重新发送。

发布后先登录提醒中心，让索引初始化并确认配置状态，再手动测试 FC。无到期事项时应204且不创建 SQL 连接，页面从“等待定时提醒服务连接”变为正常。503需要检查索引或签名，不应改用分钟 SQL 扫描。受控验收通过后再开启1分钟触发器和邮件总开关，并分别绑定设备及邮箱。

故障时可独立关闭 FC 触发器，或把 `REMINDER_EMAIL_ENABLED=false` 后重新部署。账号邮件开关立即约束后续请求；站内和日历数据保留，新增表及回执不删除。

恢复采用修复提交重新部署。不要直接恢复不兼容的旧 QStash 版本：旧代码不识别新通道回执，可能重复发送。QStash 未实际验证，不能作为现成回退服务。需要回退功能时保持当前兼容代码，关闭外部调度/邮件，明确使用站内与日历模式。
